Архитектура Todo-листа
1. Назначение системы
Todo-лист - система управления задачами. Пользователи могут создавать
проекты, добавлять в них задачи и отслеживать выполнение.

В системе используются три основных класса: User, Project и Task.
2. Класс User - пользователь
Ответственность: хранить информацию о пользователе и список
проектов, с которыми он работает.
Атрибуты
- id - уникальный идентификатор пользователя.
- name - имя пользователя.
- email - адрес электронной почты.
- projects - список проектов пользователя.
Методы
- create_project(name, description) - создать проект и добавить
  его пользователю.
- add_project(project) - добавить существующий проект в список
  пользователя.
- remove_project(project_id) - убрать проект из списка
  пользователя.
- get_projects() - получить список проектов пользователя.
3. Класс Project - проект
Ответственность: объединять задачи, относящиеся к одной цели или
области работы.
Атрибуты
- id - уникальный идентификатор проекта.
- name - название проекта.
- description - описание проекта.
- tasks - список объектов Task, входящих в проект.
- owner - пользователь, которому принадлежит проект.
Методы
- add_task(task) - добавить задачу в проект.
- remove_task(task_id) - удалить задачу из проекта.
- get_task(task_id) - найти задачу по идентификатору.
- get_all_tasks() - получить все задачи проекта.
- get_completed_tasks() - получить выполненные задачи.
- get_pending_tasks() - получить задачи, которые ещё не выполнены.
4. Класс Task - отдельная задача
Ответственность: хранить данные одной задачи и управлять её
состоянием.
Атрибуты
- id - уникальный идентификатор задачи.
- title - короткое название задачи.
- description - подробное описание задачи.
- status - статус, например «не выполнена» или «выполнена».
- priority - приоритет: низкий, средний или высокий.
- created_at - дата и время создания.
- due_date - срок выполнения; необязательный.
- assignee - пользователь, назначенный исполнителем;
  необязательный.
Методы
- mark_completed() - отметить задачу выполненной.
- mark_pending() - вернуть задачу в состояние «не выполнена».
- update_title(new_title) - изменить название.
- update_description(new_description) - изменить описание.
- change_priority(new_priority) - изменить приоритет.
- assign_to(user) - назначить пользователя исполнителем.
- set_due_date(date) - установить срок выполнения.
5. Как классы и объекты взаимодействуют
1. Создаётся объект User, представляющий пользователя системы.
2. Пользователь вызывает create_project(). Создаётся объект
   Project, который связывается с пользователем и добавляется в его
   projects.
3. Чтобы добавить дело, создаётся объект Task.
4. Объект Project добавляет задачу в свой список через add_task().
5. При необходимости проект назначает задаче исполнителя через
   Task.assign_to(user).
6. Когда задача выполнена, вызывается Task.mark_completed().
7. Проект может получить все задачи, только выполненные задачи или
   задачи, ожидающие выполнения.
8. Пользователь может просмотреть список своих проектов.
6. Пример сценария
Допустим, пользователь хочет организовать учебные задачи по Python.
1. Создаётся пользователь User с именем и электронной почтой.
2. Пользователь создаёт проект Project с названием «Обучение Python».
3. В проект добавляются задачи Task: «Пройти урок», «Написать код» и
   «Загрузить домашнее задание».
4. Одну из задач при необходимости назначают исполнителю.
5. После выполнения задачи её статус меняют на «выполнена».
6. Проект показывает, какие задачи уже завершены, а какие ещё остались.
7. Связи между классами
- User --- Project: один пользователь может иметь несколько
  проектов. У проекта есть владелец.
- Project --- Task: один проект содержит несколько задач. В
  базовой версии задача относится к одному проекту.
- User --- Task: пользователь может быть назначен исполнителем
  задачи. Это необязательная связь: задача может быть без исполнителя.
8. Почему система разделена на три класса
- User отвечает за пользователя и его проекты.
- Project отвечает за группировку и управление задачами в рамках
  проекта.
- Task отвечает за данные и состояние отдельной задачи.
У каждого класса своя зона ответственности. Благодаря этому код проще
читать, тестировать и расширять. Например, позже можно добавить дедлайны
с напоминаниями, роли пользователей или сохранение данных в базу, не
объединяя всю логику в одном классе
